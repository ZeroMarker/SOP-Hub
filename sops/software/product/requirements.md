## 1. 目的

规范软件产品需求从收集、分析、设计、评审、变更到验收的全过程，确保需求来源清晰、价值明确、边界完整、交付可验证。

## 2. 适用范围

适用于新产品规划、功能迭代、客户定制需求、内部运营需求、合规需求和缺陷优化需求的管理。

## 3. 术语与定义

| 术语 | 定义 |
|------|------|
| PRD | 产品需求文档，描述需求背景、目标、范围、流程、规则和验收标准 |
| 用户故事 | 从用户视角描述目标、场景和价值的需求表达方式 |
| 需求池 | 统一收集和管理待评估需求的列表 |
| 需求优先级 | 基于价值、紧急度、成本和风险确定的需求排序 |
| 验收标准 | 判断需求是否完成的明确条件 |
| MVP | 最小可行产品，用最小功能集合验证核心价值 |

## 4. 职责分工

### 4.1 产品经理
- 收集、分析和维护需求
- 编写 PRD、原型和验收标准
- 组织需求评审和需求验收
- 管理需求变更和版本范围

### 4.2 业务/运营方
- 提供业务目标、用户场景和数据依据
- 参与需求价值评估和验收
- 确认上线后的运营方案

### 4.3 研发负责人
- 评估技术可行性、工作量和技术风险
- 提供技术方案建议
- 确认开发排期和依赖条件

### 4.4 测试负责人
- 评估需求可测试性
- 明确测试范围和验收口径
- 参与需求评审和验收

### 4.5 设计师
- 输出交互原型和视觉方案
- 参与用户体验和可用性评估
- 确保设计稿与需求一致

## 5. 操作流程

### 5.1 需求收集流程

```
需求来源登记 → 需求初筛 → 需求归类 → 需求池维护 → 定期评估
```

**需求来源：**

- 用户反馈和客服工单
- 业务运营诉求
- 数据分析发现
- 市场竞品分析
- 合规、安全和技术治理要求
- 管理层战略规划

**登记要求：**

- 需求标题、提出人、提出时间
- 业务背景和目标
- 受影响用户或业务范围
- 期望上线时间
- 相关数据、案例或附件

### 5.2 需求分析流程

```
场景分析 → 用户价值评估 → 业务规则梳理 → 边界条件确认
→ 指标定义 → 优先级评估
```

**分析要点：**

1. 明确目标用户、使用场景和核心痛点
2. 明确当前流程、目标流程和差异点
3. 明确主流程、异常流程、权限规则和数据规则
4. 明确成功指标和上线后观测指标
5. 评估业务价值、开发成本、风险和依赖

### 5.3 PRD 编写流程

```
文档编写 → 原型设计 → 规则补充 → 自查修订 → 提交评审
```

**PRD 必含内容：**

- 背景与目标
- 需求范围和不做范围
- 用户角色和使用场景
- 页面原型和交互说明
- 业务规则、权限规则和数据规则
- 接口、埋点、通知、配置等补充需求
- 验收标准和上线指标

### 5.4 需求评审流程

```
评审预约 → 材料预读 → 会议评审 → 问题记录
→ 文档修订 → 评审确认
```

**评审要求：**

- 评审材料至少提前 1 个工作日发出
- 产品、研发、测试、设计必须参与核心需求评审
- 评审问题需明确责任人和完成时间
- 未关闭的关键问题不得进入开发

### 5.5 需求变更流程

```
变更提出 → 影响评估 → 变更审批 → 文档更新
→ 排期调整 → 相关方同步
```

**变更控制：**

- 已进入开发阶段的需求变更必须评估影响
- 影响排期、成本或范围的变更需项目负责人审批
- 所有变更必须同步更新 PRD、原型、测试用例和任务

## 6. 特殊情况处理

### 6.1 紧急需求
- 明确紧急原因和业务损失
- 采用快速评审机制
- 保留最低限度 PRD 和验收标准
- 上线后补齐完整文档和复盘记录

### 6.2 客户定制需求
- 明确是否可产品化
- 评估维护成本和通用性
- 单独记录客户范围、交付标准和验收人

### 6.3 需求争议
- 回到业务目标和用户价值进行判断
- 必要时提交产品委员会或业务负责人决策
- 决策结果记录在需求文档中

## 7. 服务质量要求

| 项目 | 标准 |
|------|------|
| PRD 完整率 | 核心需求 100% |
| 需求评审覆盖率 | 进入开发需求 100% |
| 验收标准明确率 | 100% |
| 需求变更记录完整率 | 100% |
| 评审问题关闭率 | 开发前 100% |
| 上线指标定义率 | 重点需求 100% |

## 8. 信息安全管理

- 涉及用户隐私、支付、权限和数据导出的需求必须进行安全评估
- PRD 中不得暴露真实密钥、生产账号或未脱敏用户数据
- 外部客户需求文档需控制访问权限
