## 1. 目的

规范硬件项目从需求输入到立项评审的全流程，确保功能、性能、成本、交期四要素在动手设计前收敛，避免中途大改与选型返工。

## 2. 适用范围

适用于新品硬件开发与重大改版（换主控/改架构/新增认证）项目；小改款可走简化流程（见6.1）。

## 3. 术语与定义

| 术语 | 定义 |
|------|------|
| HRS | 硬件需求规格书，功能/性能/接口/功耗/环境的量化描述 |
| EVT/DVT/PVT | 工程验证/设计验证/生产验证三阶段试产 |
| BOM成本 | 物料清单成本，不含研发费用与分摊 |
| 关键器件 | 主控/电源/射频/传感器等决定架构与交期的器件 |
| 长交期料 | 货期≥12周的器件，需提前备货或找替代 |

## 4. 职责分工

### 4.1 产品经理
- 输出产品需求（功能/场景/销量预测/目标售价），组织立项评审

### 4.2 硬件负责人
- 输出HRS与系统架构初案，评估技术可行性与风险
- 给出关键器件选型方向与BOM成本区间

### 4.3 采购部
- 反馈关键器件货期、价格趋势、停产（EOL）风险
- 输出供应链可行性意见

### 4.4 项目经理
- 制定项目计划（EVT/DVT/PVT节点），跟踪立项action关闭

## 5. 操作流程

### 5.1 需求输入与HRS编制

```
产品需求 → 硬件需求分解 → HRS初稿
```

1. **需求分解**：每条产品需求必须转化为可测试的硬件指标（例：“续航7天”→电池容量/平均功耗/休眠电流三级指标）
2. **HRS必含章节**：功能清单、性能指标、接口定义、功耗预算、结构尺寸约束、环境等级（温度/防水/跌落）、认证要求（CE/FCC/3C）、目标BOM成本
3. **量化红线**：模糊词（“尽量小”“足够快”）一律打回，改写为数字+测试条件

### 5.2 可行性评估与立项评审

```
架构初案 → 成本/货期评估 → 立项评审会 → 立项下发
```

1. **架构初案**：系统框图+关键器件候选（主控/电源拓扑/无线方案至少两选一对比）
2. **双评估**：
   - 成本评估：BOM成本vs目标售价，成本率超红线必须有降本路径或溢价理由
   - 供应评估：长交期料清单+替代料预案，无双货源的关键器件标记风险
3. **立项评审会**：产品/硬件/软件/结构/采购/品质六方到场，结论三类：通过/有条件通过（限期整改项）/驳回
4. **立项下发**：冻结HRS V1.0与项目计划；冻结后需求变更走ECR（见6.2）

## 6. 特殊情况处理

### 6.1 小改款简化流程
- 仅改外设/接口/结构且不动主控架构的，可跳过架构初案，HRS以差异表形式输出，评审压缩为邮件会签

### 6.2 立项后需求变更
- 走ECR：评估硬件改动量+器件损失+计划影响，三方（产品/硬件/项目）签字；EVT后变更默认顺延至下一版，除非客户书面要求

### 6.3 关键器件EOL/涨价
- 采购预警后2周内硬件给出替代验证计划；已立项项目换关键器件必须重开架构评审

## 7. 服务质量要求

| 项目 | 标准 |
|------|------|
| HRS指标可测试率 | 100%（每条指标有测试方法） |
| 立项评审结论当场输出率 | 100% |
| 有条件通过项按期关闭率 | 100% |
| EVT后需求变更率 | ≤ 10%（条目数口径，逐季下降） |

## 8. 信息安全管理

- HRS、架构图、BOM成本为机密，仅立项评审成员传阅
- 对外（方案商/供应商）分段提供需求，完整HRS不外发
- 立项资料归档PLM/网盘，版本受控
